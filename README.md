# DOT 5m Trading Bot

A personal, single-user research and (eventually) execution project for one
mechanical strategy on `DOT-USDT-SWAP` (OKX perpetual futures), 5-minute
timeframe. It is not a product, not multi-tenant, and not investment advice.
Nothing here recommends that anyone trade this or any other strategy; it is
the author's own tooling for measuring whether a specific, fully-frozen rule
set makes or loses money before any real capital touches it.

The full, authoritative specification (signal rules, trade levels, position
sizing formula, order execution policy, phase plan, execution safety
requirements) lives in [CLAUDE.md](CLAUDE.md). This file only summarizes it
and describes the code. If the two ever disagree, CLAUDE.md is correct and
this file is stale.

## Spec summary

Instrument `DOT-USDT-SWAP`, 5m closed candles only, cross margin, 50x
leverage ceiling (a margin-efficiency ceiling, not the risk control - the
stop-loss is). Signal: three consecutive "strong" candles (body > 50% of
range) in the same direction, with EMA12/26/100 stacked the same direction.
Entry at the signal candle's close; SL at the low/high of the oldest of the
three candles; TP at 2R. One position at a time; a new signal while a
position is open is ignored, never queued. Position size: risk exactly 2% of
current equity, computed from live-fetched `ctVal`/`lotSz`/`minSz`/`tickSz`,
always rounded down. Entry and SL are taker (market); TP is maker (resting
limit). Full detail, rationale, and the execution-safety requirements are in
CLAUDE.md - this paragraph is intentionally incomplete.

## Project structure

```
src/
  types.ts              Candle/Signal types, at() (throwing array index), shared time constants
  okxClient.ts           Low-level OKX REST client: candles, instrument spec, funding rate history (retry/backoff)

  fetchData.ts            CLI: fetch/resume 5m and 1m candle history to data/*.json
  fetchInstrument.ts       CLI: fetch and cache the live instrument spec (ctVal/lotSz/minSz/tickSz/lever)
  fetchFundingHistory.ts   CLI: fetch and cache available OKX funding-rate-history (limited retention)
  validateData.ts          CLI: report duplicates/gaps/out-of-order/OHLC violations in cached candle data
  dataIntegrity.ts         validateCandles(), splitIntoContiguousSegments() - used by validateData and the backtest

  signal.ts                computeSignal(): the frozen signal rule, pure (Candle[]) -> Signal | null
  signalScan.ts             generateSignals(): slides computeSignal across a contiguous segment
  tradeSequencer.ts         sequenceTrades(): one-position-at-a-time sequencing with real TP/SL touch semantics
                             (used by analyze.ts; backtestEngine.ts has its own equity-aware version, see below)

  instrumentSpec.ts         InstrumentSpec type + loader/validator for the cached instrument spec
  decimal.ts                floorToStep/ceilToStep/roundToStep - decimal-safe rounding to an exchange step size
  positionSizing.ts         computePositionSize(): the frozen 2%-risk sizing formula, pure
  funding.ts                8h funding boundary math (00:00/08:00/16:00 UTC): isFundingTs, countFundingCrossings

  stats.ts                  percentile/mean/sum/monthKey helpers shared by analyze.ts and backtestEngine.ts
  backtestEngine.ts          The Phase 2 engine: signal prep, per-scenario equity-aware simulation
                             (runScenario), and metrics (computeMetrics, splitMetrics). Pure - no file I/O.
  backtest.ts                CLI: loads data + spec, runs every {slippage x ambiguous-bound x fee-model}
                             scenario through backtestEngine.ts, prints the report, writes data/backtest-*.

  analyze.ts                 CLI: Phase 1 measurement (signal counts, SL-distance distribution, survival
                             count) - a lighter-weight tool than backtest.ts, no fees/sizing/equity.

  *.test.ts                  node:test unit tests, colocated with the module they cover
```

### Why `tradeSequencer.ts` and `backtestEngine.ts` both sequence trades

`analyze.ts` (Phase 1) only needs to know which signals survive the
one-position-at-a-time rule and how they'd exit on a touch basis - it has no
concept of equity or position sizing. `backtestEngine.ts` (Phase 2) needs
real P&L, and whether a signal actually opens a position depends on position
sizing, which depends on current equity, which depends on every prior
trade's realized P&L *in that specific scenario*. A signal sizing rejects
(equity too small, or the target risk floors to under `minSz`) never opens a
position and so does not block the next signal - unlike a signal that is
ignored because a real position is still open. That equity-feedback loop is
why `backtestEngine.ts` cannot just reuse `tradeSequencer.ts`'s output as a
fixed sequence and replay fills on top of it; instead it precomputes each
signal's *natural* resolution (scenario-independent - just "where would this
exit if it were the only position") once, then walks the chronological
signal list per scenario, sizing and filling inline. See the comment on
`runScenario` in `backtestEngine.ts` for the full reasoning.

## Data flow

```
OKX public REST API
  |
  |-- GET /market/history-candles  --> fetchData.ts       --> data/DOT-USDT-SWAP-5m.json
  |                                                            data/DOT-USDT-SWAP-1m.json
  |-- GET /public/instruments      --> fetchInstrument.ts --> data/instrument-DOT-USDT-SWAP.json
  |-- GET /public/funding-rate-history --> fetchFundingHistory.ts --> data/funding-rate-history-DOT-USDT-SWAP.json

data/*.json
  |
  |-- validateData.ts   --> console report (integrity only, no trading logic)
  |
  |-- analyze.ts   --> signal.ts + signalScan.ts + tradeSequencer.ts + dataIntegrity.ts
  |                --> console report (Phase 1 measurement)
  |
  \-- backtest.ts  --> instrumentSpec.ts + backtestEngine.ts
                       (which itself uses signal.ts, signalScan.ts, positionSizing.ts,
                        decimal.ts, funding.ts, stats.ts)
                   --> console report
                   --> data/backtest-report.txt   (same report, as text)
                   --> data/backtest-results.json (full metrics for every scenario)
```

`data/` is gitignored - every file in it is either fetched from OKX or
generated by a script, and is reproduced by rerunning the relevant command.

## Running

All commands run from the repository root, via `npm run <script>`.

```bash
npm run typecheck            # tsc --noEmit
npm test                     # node:test over every src/*.test.ts
```

```bash
npm run fetch-data                        # resume/extend 5m and 1m history backward (default: both bars)
npm run fetch-data -- --bar 5m            # only 5m (also: --bar 1m, --bar both)
npm run fetch-data -- --from 2021-01-01   # anchor a fresh fetch (ignored once data already exists to resume from)
npm run fetch-data -- --to 2021-06-01
npm run fetch-data -- --forward           # catch up to now from whatever is already on disk (cannot combine with --from/--to)
```

```bash
npm run fetch-instrument       # fetch and cache the live instrument spec (run before position sizing/backtest)
npm run fetch-funding-history  # fetch and cache available funding-rate-history (OKX retains only a few months)
```

```bash
npm run validate     # integrity report for data/DOT-USDT-SWAP-{5m,1m}.json
npm run analyze       # Phase 1 measurement report (signal counts, SL-distance distribution, survival count)
npm run backtest       # Phase 2 full backtest: all scenarios, in-sample/out-of-sample, writes data/backtest-*
```

`fetch-data`, `fetch-instrument`, and `fetch-funding-history` only hit
public, unauthenticated OKX endpoints - no API keys are needed for anything
in this repository yet (Phase 3+ will need trade-permission keys, per
CLAUDE.md section 6).

## Notes and known limitations

- **Funding cost is a constant-rate approximation.** OKX's
  `funding-rate-history` endpoint only retains a few months (empirically,
  about 3 months for `DOT-USDT-SWAP`), while the backtest covers 2020-08 to
  present. `backtest.ts` measures what fraction of trades hold across a
  funding settlement first; if that is material (>=5%, per CLAUDE.md section
  4), it applies the *mean realized rate from the available window* as a
  constant proxy to every crossing across the full history, and says so in
  the report. This is disclosed as an approximation, not a real historical
  cost - there is no way to get the real rate for periods OKX no longer
  retains.
- **1m data is not backfilled to the full history.** It exists to resolve
  "TP and SL both touched in the same 5m bar" (see CLAUDE.md section 5,
  "Intrabar ambiguity"), and per that section is only worth fetching for the
  specific periods containing ambiguous trades if the lower/upper bound
  backtests straddle zero. In the current Phase 2 run they do not (both
  bounds lose money), so 1m data was not needed for this purpose.
